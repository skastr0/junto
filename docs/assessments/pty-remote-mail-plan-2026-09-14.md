# Remote mailbox delivery plan

2026-09-14. Source reviewed through `821dcead`; Remote mail was deliberately left unsupported by `3b744c2c`. This is a proposed implementation contract, not Remote runtime evidence. Finish the local packaged-app correctness gate independently.

## Decision pending contract resolution

Prefer additive delivery-input journal/outbox storage in the existing product database, transported through a typed field on the existing CC-to-Remote `report` exchange. Derive an installation-local mailbox view from that retained input. Keep canonical mailbox rows on Command Center. Use existing `delivery.accepted` receipts only for actual managed-transport acceptance or the existing explicit read operation.

The precise envelope, persistence, paging and staging-ACK contract must be resolved before implementation. This proposal needs an additive schema migration, not another Station operation, database, or canonical mailbox replica. Delivery-input acknowledgements are not aliases for accepted receipts.

**Migration boundary:** the governing [routine migration law](../../AGENTS.md#L127) forbids deleting, overwriting, renaming, dropping or reusing existing durable names; [physical retirement](../../AGENTS.md#L136) requires separate review and explicit operator approval. The source helper `replacesTables` permits DROP/recreate ([migrations.ts:101](../../src/main/vellum-command/state/migrations.ts#L101)), but capability is not authority. Its use here would conflict with that law. Do not prescribe a copy/drop/recreate migration or treat historical examples as approval. Preserve existing tables unchanged and prefer additive storage; any alternative crossing this boundary requires resolution before implementation. The local build gate is unaffected.

### Why not a `project` sidecar?

There is no mailbox sidecar in the current `ProjectRequest`: it carries only a complete authorial `StationProjectionBody` ([station-api.ts:192](../../src/shared/station-api.ts#L192)). The install transaction stores that body and its intent identities ([station/repository.ts:1060](../../src/main/vellum-command/station/repository.ts#L1060)); notification runs only when intent installation changes ([station/api.ts:2265](../../src/main/vellum-command/station/api.ts#L2265)). Putting mail inside the existing portfolio body is currently rejected as runtime Work projection ([portfolio.ts:129](../../src/main/vellum-command/station/portfolio.ts#L129)).

A typed field beside `projection` is legal to propose. However, independent mail changes would need their own identity/hash, durable install, acknowledgement, size limits, membership/withdrawal semantics, and notifications even when intent is unchanged. An in-memory sidecar loses full bodies on restart. A durable sidecar needs product-schema changes too, or an explicitly defined way to journal it. Coupling mail changes to authorial projection generations gives unrelated data one lifecycle. Prefer a typed `report` field because report already exchanges bounded pages and acknowledgements, but explicitly define its new delivery-input bounds and acknowledgement semantics; existing Work cursors do not automatically cover a sidecar. Compare this with an independently persisted `project` sidecar at contract freeze.

Existing events alone are insufficient. CC does not broadcast its CC/CC fact route; `selectStationReportRoutes` selects only CC-to-peer commands ([api.ts:262](../../src/main/vellum-command/station/api.ts#L262)). CC mailbox facts returned to a Remote are exact outcomes of that Remote's sender commands, not a recipient subscription. Filtering arbitrary mailbox facts out of that route would violate contiguous sequence admission. Remote mailbox materialization is intentionally skipped ([repository.ts:9801](../../src/main/vellum-command/work/repository.ts#L9801)), consistent with [mailbox residency](../vellum-protocol.md#L829).

## Contract to freeze

A new Work command could reuse existing command identities and resolution, but its operation/item would not fit the closed SQL CHECK domains in `work_events` and `work_pending_commands` ([state-schema.ts:325](../../src/main/vellum-command/work/state-schema.ts#L325), [708](../../src/main/vellum-command/work/state-schema.ts#L708)). It is not an approved implementation shortcut. The preferred additive alternative is a typed delivery-input envelope, durably installed in a new journal before its staging ACK. That ACK means **input durably installed**, never “prompt delivered.” Do not disguise staging as `message.append` or `delivery.accepted`, or reuse a Work route cursor for a different sequence. The current command engine's synchronous fact/disposition behavior ([repository.ts:7422](../../src/main/vellum-command/work/repository.ts#L7422)) is a comparison point, not an existing implementation of this envelope.

Each input carries:

- Canonical CC identity, mailbox sink, message ID, exact recipient `ActorRef`, and the target installation. Input identity includes that recipient binding; equal message text never equates two messages.
- The source message fact ID/hash and the complete immutable `Message`, including inline text parts. A reused source identity with different body bytes is rejected. Intent witnesses authorize the current recipient; a source message's historical intent hash is provenance, not a requirement that today's whole canvas hash remain unchanged.
- An explicit available/withdrawn state and predecessor-ordered revisions. Absence from a partial report page does not withdraw anything. There is no wall-clock expiry. A later explicit withdrawal or current projected actor removal/movement denies local delivery and exposure; offline execution uses the last received intent, so an offline Remote cannot know a later revocation.
- CC-known canonical delivery/read receipt identities and acceptance values, represented as **projection observations**, not fabricated local receipt facts. Local committed receipts take precedence over an older observation; missing observations cannot clear acceptance. Freeze the exact typed representation and validation with the existing canonical ID functions. Do not invent a second spelling of a mailbox receipt.

An accepted notification does not remove the full body. Long messages are intentionally summarized into a prompt directing the agent to `vellum-command msg list` ([message-delivery.ts:114](../../src/shared/message-delivery.ts#L114)). Keep their text available after notification acceptance and explicit read, subject to current actor access. Withdrawal concerns access/membership, not routine delivery completion. Retained journal bytes are not deleted by withdrawal.

CC creates or reconciles inputs from canonical mailbox state and current placement. The append-to-input scheduling gap must recover through durable enumeration on startup/reconnect; an append callback and process `Set` are insufficient. Reconnect resends the same pending input identity, not a new logical input. A receipt or placement change creates a causally ordered input revision. CC-to-one-Remote inputs must never fan out unrelated mailbox bodies to another Remote.

## Implementation seams and ownership

1. **Contract/schema lane:** resolve the additive report-input versus independently persisted project-sidecar choice; update `docs/vellum-protocol.md`, `src/shared/station-api.ts` and both Station codec endpoints together. The six Station operations stay unchanged. Prerelease protocol 1 permits deliberate codec evolution; it does not make an older codec understand a new field. Test explicit incompatible-peer refusal. Append schema `23 → 24` with new delivery-input journal/outbox storage while preserving all existing table definitions and rows. Freeze exact input identity, revisions, integrity hashes, peer-scoped paging, byte/record limits and durable staging ACKs. Do not edit historical migrations or widen existing CHECKs through DROP/recreate.
2. **Repository/Station lane:** implement CC input reconciliation, exact source/recipient validation, atomic durable input installation before staging ACK, and a journal-derived input query. Preserve existing Work record sequencing and ACK behavior. Input installation must not insert `work_messages` or `work_delivery_receipts`. Retain input bodies after staging ACK so restart can reconstruct the view; ACK permits transport progress, not prompt acceptance or body deletion. Keep delivery-input cursor/state distinct from Work cursors and include both payloads in report size admission.
3. **Projection/control lane:** merge the authorized input view into the common `CanvasesService` Work projection so delivery rereads, CLI reads, and `workMessageMarkRead` see the same messages. A delivery-only cache is insufficient. Explicitly account for sinks with no material rows: current membership enumerates six material tables and excludes the event journal ([repository.ts:3753](../../src/main/vellum-command/work/repository.ts#L3753)). Existing Work-event insertion increments the canvas revision ([state-schema.ts:2248](../../src/main/vellum-command/work/state-schema.ts#L2248)); new input tables will need their own explicit revision/invalidation integration. Rebuild on boot, invalidate after ingress, and notify delivery scheduling even with unchanged authorial intent.
4. **Runtime composition lane:** only then compose Remote mail through the real `MessageDeliveryService` and managed drive. Revalidate source membership, recipient binding, current intent and receipts before physical writes, including after asynchronous waits. On proven submission, commit the existing canonical local receipt and let the Remote/Remote fact route return it to CC. A staging fact, report ACK, timeout, or accepted paste alone must not mint that receipt.

The agent-facing full-text path is `msg list`: it returns complete `Message` items and marks unread own-mailbox items read ([control.ts:1398](../../src/main/vellum-command/work/control.ts#L1398)). `msg read` currently marks read; it is not a full-body fetch API. The service checks that the message exists in the common read projection before committing its canonical read receipt ([service.ts:2747](../../src/main/vellum-command/work/service.ts#L2747)). Preserve process-bound owner admission. Mailbox media remains a separate contract gap: current content materialization authorization follows task attachments, so a mailbox-only `ContentRef` needs explicit own-mailbox authorization and existing content transfer. Do not claim attachment support from text-list success or introduce arbitrary content access. Oversize records must fail visibly under report bounds, never silently truncate full bodies.

## Required evidence before enabling Remote mail

Use two real StateEngine/WorkRepository/StationApi compositions with temporary databases, then the actual Node Remote process and registered agent CLI. Component mocks alone do not clear this feature.

- CC appends long text to Remote A amid unrelated CC mail. A receives exactly its staged input through bounded report pages; Remote B receives no body. Remote `work_messages` remains empty.
- Staging is ACKed before any PTY write. No delivery/read receipt exists. Restart Remote and reconstruct the pending input from its journal. In a separate read case, registered `msg list` returns the complete body and creates only the legitimate read receipt.
- Exercise individual and batch mail at the real service-to-drive seam: pre-write refusal can retry; accepted paste left unresolved produces no accepted receipt or destructive repaste; successful submission persists the canonical receipt and repeated reports/idle cycles do not reinject it.
- Crash/reconnect after durable receipt suppresses retries and converges CC metadata. Crash after physical acceptance but before receipt commit remains an explicitly documented possible redelivery window. Raw PTY transport cannot supply durable exactly-once acceptance ([protocol receipt boundary](../vellum-protocol.md#L722)).
- Duplicate input envelopes, partial pages, interrupted reconnect, same text with different message IDs, conflicting hashes, newer receipt observations, withdrawal, movement, and delayed old revisions cannot restore stale membership or regress receipts. Full bodies remain readable after notification acceptance.
- The additive migration preserves existing schema-23 table definitions, messages, events, command resolutions, receipt identities, hashes and cursors unchanged. Prove both codec ends and actual Node Remote CLI retrieval before enabling composition. Finally capture Remote process/transport provenance and a real harness response; local Electron/native success is not Remote evidence.

This plan establishes the missing delivery source and durable recovery contract. It does not qualify fourteen harnesses, prove native Remote delivery, or close the unavoidable external-transport crash window.
